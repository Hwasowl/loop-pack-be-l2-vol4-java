# Round 7 — 이벤트/Kafka 설계 의사결정 문서

> 이 문서는 "무엇을·왜 이렇게 만들었는가"와 "다음에 무엇을 해야 하는가"를 담는 **개발 문서**다.

---

## 1. 개요

### 문제 정의

기존 주문·좋아요 흐름은 부가 로직(집계 반영, 결제 알림, 행동 로그)까지 **하나의 트랜잭션**에 묶여 있었다. 이 구조는 두 가지 문제를 낳는다.

1. **결합**: 집계·로깅이 실패하면 본질(주문/좋아요)까지 롤백된다. 부가 로직이 본 트랜잭션의 성공을 인질로 잡는다.
2. **경계 확장 불가**: 트랜잭션 안에 외부 I/O(알림, 다른 서비스 통지)가 들어오면 락 점유 시간이 늘고, 서비스 분리 시 그 트랜잭션을 넘을 방법이 없다.

### 목표

- "이 작업이 실패하면 본 트랜잭션도 실패해야 하는가"를 기준으로 부가 로직을 분리한다.
- 서비스 경계를 넘는 이벤트는 **DB 커밋과 발행을 원자적으로 묶어** 유실 없이(At Least Once) 전달한다.
- 소비 측은 **중복 수신을 전제로** 멱등하게 처리한다.
- 같은 뼈대를 선착순 쿠폰 발급에 적용해 순간 폭주를 순차 처리로 흡수한다.

---

## 2. 아키텍처 개요

실행 단위는 **commerce-api**(발행 + 일부 소비)와 **commerce-streamer**(집계 소비)로 나뉘고, 그 사이를 Kafka가 잇는다.

### 토픽 구성

| 토픽 | partition key | 파티션 | 용도 |
|---|---|---|---|
| `catalog-events` | productId | 3 | 좋아요/조회/판매 → 상품 집계 |
| `order-events` | orderId | 3 | 결제 완료/실패 → 주문 후처리 |
| `coupon-issue-requests` | couponId | 3 | 선착순 발급 요청(순차 처리용) |
| `user-actions` | userId | 3 | 유저 행동 로그(append-only) |
| `*-dlq` | 원본 key | 1 | 처리 실패 격리(수동 재처리) |

파티션 수는 브로커 auto-create 디폴트(1)에 맡기지 않고 `KafkaTopicConfig`에서 **코드로 고정**한다. 키가 서로 다른 메시지를 파티션에 분산해 병렬 소비하고, consumer concurrency(3)와 맞춘다.

---

## 3. 핵심 설계 결정

각 결정은 **문제 → 선택지 → 결정 → 트레이드오프** 순으로 정리한다.

### 3.1 트랜잭션에서 무엇을 빼낼 것인가

- **문제**: 부가 로직(집계·알림·로그)을 본 트랜잭션에 둘지, 밖으로 뺄지.
- **선택지**: (a) 그대로 동기 호출 (b) `@TransactionalEventListener(AFTER_COMMIT)`로 커밋 후 분리.
- **결정**: 기준은 **"실패 시 본 트랜잭션도 실패해야 하는가"**. 필수 정합성(재고 차감 등)은 동기로 남기고, 실패해도 본질이 유지돼야 하는 것(상품 판매 집계, 행동 로그)은 커밋 후 이벤트로 뺀다.
- **트레이드오프**: 커밋 후 발행은 본 트랜잭션을 보호하지만, 발행 자체가 실패하면 **그 부가 효과는 유실**될 수 있다(→ 3.2에서 경계 넘는 이벤트만 outbox로 보강).

### 3.2 서비스 경계를 넘는 이벤트 — 하이브리드 Outbox

- **문제**: `AFTER_COMMIT`에서 바로 Kafka에 쏘면, **커밋은 됐는데 발행 직전 프로세스가 죽으면** 이벤트가 사라진다(DB와 브로커는 별개 자원 — 원자적이지 않다).
- **선택지**:
  - (a) **즉시 발행만** — 빠르지만 위 유실 구간이 남는다.
  - (b) **폴링(릴레이)만** — 유실은 없지만 항상 폴링 지연(초 단위)이 붙는다.
  - (c) **하이브리드** — 즉시 발행을 1차로, 폴링을 백업으로.
- **결정**: **(c) 하이브리드**.
  - 커밋 직전(`BEFORE_COMMIT`) outbox row를 **같은 트랜잭션으로 저장** → DB 커밋과 outbox 기록이 원자적.
  - 커밋 직후(`AFTER_COMMIT`, `@Async`) **즉시 발행 시도**(가속기, best-effort).
  - **릴레이 폴링**이 백스톱 — 즉시 발행이 성공했으면 이미 PUBLISHED라 건너뛰고, **grace(기본 60초)를 넘긴 미발행 건만** 주워 발행한다.
- **트레이드오프**: 폴링을 "주 로직"이 아니라 **백업본**으로 신뢰한다. grace는 *즉시 발행과의 경합만 피할 만큼*(즉시 발행 타임아웃 5초보다 넉넉한 60초)으로 짧게 둔다 — 길게(예: 10분) 잡으면 즉시 발행이 실패한 정상 건까지 그만큼 방치돼 유실 불허 경로에 불필요한 정합성 지연이 생긴다. 정상 건은 즉시 발행이 처리하고, 실패한 소수만 60초 뒤 폴링이 복구한다.

### 3.3 Outbox 3-state (PENDING / PUBLISHED / FAILED)

- **문제**: 미발행/발행완료 2상태만 두면, **영구 실패(poison)** 메시지를 폴링이 계속 다시 집는다.
- **결정**: `FAILED`를 추가해 **DLQ로 격리한 건**(역직렬화 불가, 재시도 5회 초과)을 PUBLISHED와 구분하고 재폴링 대상에서 뺀다.
- **유실 방지 안전장치**: `FAILED`는 유실이 아니라 회수 대상이다 — FAILED로 넘기기 전에 그 이벤트를 `order-events-dlq`로 격리하므로 재처리 API로 되살릴 수 있다. 단 브로커 다운이면 DLQ 발행(같은 브로커)도 실패하므로, **격리가 실제 성공했을 때만 FAILED로 굳히고** 실패하면 PENDING으로 남겨 재시도한다(FAILED로 종결하는 순간이 곧 유실이기 때문). 남은 과제는 FAILED/DLQ 적재 **알림**(§6).
- **트레이드오프**: 상태 컬럼·인덱스가 늘지만, 폴링 쿼리가 (status, created_at) 인덱스로 좁아지고 poison이 파티션을 막지 않는다.

### 3.4 소비 멱등성

At Least Once라 **중복 수신을 전제**한다. 토픽 성격별로 멱등 전략을 다르게 둔다.

| 토픽 | 멱등 전략 |
|---|---|
| `order-events` | 주문 **상태 가드**(이미 처리된 상태면 무시) |
| `catalog-events`(판매) | `event_handled` 테이블 PK로 중복 차단 |
| `catalog-events`(좋아요) | **스냅샷 latest-wins**(오래된 이벤트는 timestamp로 버림) |
| `coupon-issue-requests` | `requestId` inbox로 중복 요청 무시 |
| `user-actions` | 없음 — append-only 로그라 유실/중복에 관대 |

### 3.5 선착순 쿠폰 — Kafka 직렬화 + DB 원자 UPDATE (Redis 미사용)

- **문제**: 순간 폭주하는 발급 요청에서 **재고 초과 발급**과 **1인 다중 발급**을 막아야 한다.
- **선택지**: Redis 분산 락/카운터 vs Kafka 파티션 직렬화 + RDB.
- **결정**: **Redis 없이** 간다.
  - `key=couponId`로 발행 → **같은 쿠폰 요청은 같은 파티션 = 순차 처리**.
  - 재고는 조건부 원자 UPDATE `WHERE issued_quantity < total_quantity`로 차감 — **DB가 카운터이자 락**.
  - `requestId` 멱등(중복 요청)과 발급 이력 exists 체크(1인1매)를 함께 둔다.
- **트레이드오프**:
  - 장점: 인프라(Redis) 추가 없이 정합성 확보, 요청 폭주를 파티션 큐가 버퍼링.
  - 한계: **단일 쿠폰의 처리량 천장** — 같은 key는 한 파티션에서 직렬이라, 하나의 인기 쿠폰은 파티션을 늘려도 병렬화되지 않는다(hot row). 1인1매 exists 체크는 **리밸런스 순간의 경계**에서 이론적 이중 처리 여지가 있다(→ §5 한계).

### 3.6 실패 격리 — DLQ

역직렬화 불가·비즈니스 예외 메시지는 컨슈머가 `<topic>-dlq`로 재발행하고 오프셋을 커밋한다. **한 건의 poison이 파티션 전체를 막지 않도록** 한다. DLQ 발행 자체가 실패해도 예외를 밖으로 던지지 않는다(파티션 진행 우선).

**재처리는 어드민 온디맨드 API**(`POST /api-admin/v1/dlq/replay?topic=`)로 한다 — `<topic>-dlq`를 읽어 원본 payload를 원본 토픽에 되돌린다(`DlqReplayer`). **자동 재시도는 하지 않는다**: 사람이 원인을 확인한 뒤 트리거해야 poison이 실패→DLQ→재주입 무한 루프에 빠지지 않는다. 전용 group으로 커밋하므로 반복 호출해도 그 사이 새로 쌓인 것만 집는다.

## 4. 데이터 모델 / 메시지 계약

- **outbox** (`outbox_event`): `aggregate_id`, `event_type`, `payload(JSON)`, `status(PENDING/PUBLISHED/FAILED)`, `retry_count`, `created_at`. 인덱스 `(status, created_at, id)`.
- **event_handled**: `event_id`(PK) — 소비 멱등 기록. `Persistable`로 구현해 save 시 불필요한 SELECT 제거.
- **메시지 타입**: `order-events`의 이벤트 타입은 공유 enum `OrderEventType`(PAYMENT_COMPLETED / PAYMENT_FAILED)로 계약을 고정한다.
- **DTO 분리**: 발행 페이로드(예: `CatalogEventPayload`)는 도메인 모델과 분리된 record로 둔다.

## 5. 현재 한계 (정직하게)

이 설계가 **아직 보장하지 못하는 것**들. 지금은 감수하고, 조건이 바뀌면 §6/§7로 옮긴다.

1. **브로커 내부 유실 구간**: 단일 브로커라 `replication-factor=1`. 브로커 디스크/노드가 죽으면 outbox가 아무리 튼튼해도 **브로커에 들어간 뒤의 메시지는 유실**될 수 있다. outbox+릴레이는 "앱→브로커" 구간만 보장한다.
2. **릴레이 단일 인스턴스 전제**: commerce-api를 여러 대로 띄우면 여러 릴레이가 같은 outbox 행을 집어 **중복 발행**할 수 있다(소비 멱등으로 흡수되지만 낭비). 분산 락/샤딩 미도입.
3. **쿠폰 hot row 처리량 천장**: 하나의 인기 쿠폰은 단일 파티션·단일 DB 행이라 수평 확장이 안 된다.
4. **쿠폰 1인1매 리밸런스 경계**: exists 체크 기반이라 컨슈머 리밸런스 순간의 이론적 이중 처리 여지가 남는다(유니크 제약으로 최종 방어 필요).
5. **`coupon-issue-requests`는 outbox를 거치지 않는다**: 발급 요청은 API 시점에 **직접 동기 발행**한다(202 접수). 발행 실패 시 클라이언트가 에러를 받고 재시도하는 전제 — order-events 같은 outbox 보장은 없다.
6. **발행 실패 관측 부재**: 즉시 발행/판매 이벤트 발행이 실패해도 로그만 남고 **메트릭·알럿이 없다**.

## 6. 다음 할 일 (Next Steps)

우선순위 순.

1. **발행 실패 메트릭 + 알럿**: outbox 릴레이가 FAILED로 격리한 건수, 판매/즉시 발행 실패를 카운터로 노출하고 Grafana 알럿을 건다(한계 6 해소). — *유실 허용 흐름이라도 급증은 장애 신호*.
2. **DLQ 재처리 고도화**: 온디맨드 재처리 API는 구현됨(§3.6). 남은 것은 (a) **개별 메시지 선택 재처리**(현재는 토픽 전량), (b) 어드민 헤더 인증 → **role 기반 인가**로 강화, (c) DLQ lag 알럿과 연동.
3. **컨슈머 재시도 정책 명시**: 일시적 오류(DB 락 타임아웃 등)는 즉시 DLQ로 보내지 말고 **정해진 횟수만큼 재시도** 후 격리하도록 `DefaultErrorHandler` 백오프를 도입한다.
4. **쿠폰 발급 요청도 outbox로**(선택): 접수 자체의 유실도 막아야 한다면 order-events와 동일한 하이브리드 outbox로 승격한다(한계 5).
5. **쿠폰 1인1매 유니크 제약**: `(coupon_id, user_id)` 유니크 인덱스로 리밸런스 경계를 DB에서 최종 차단(한계 4).

## 7. 고려사항 (Considerations)

지금 당장은 아니지만, **스케일/운영 전환 시 반드시 검토**할 것들.

- **다중 브로커 전환 시**: `replication-factor=3` + `min.insync.replicas=2` + producer `acks=all`로 브로커 내부 유실 구간(한계 1)을 닫는다. 이때 파티션 수도 함께 재검토.
- **파티션 수 변경 주의**: 이미 데이터가 쌓인 keyed 토픽의 파티션 수를 바꾸면 `key→partition` 매핑이 달라져 **기존 키의 순서 보장이 깨진다**. 파티션 수는 dev에서 확정하고, 운영에서 늘릴 때는 순서 민감도를 확인한다.
- **commerce-api 수평 확장 시**: 릴레이에 분산 락(예: DB advisory lock, ShedLock)을 걸거나 outbox를 인스턴스별로 샤딩해 중복 발행을 줄인다(한계 2).
- **graceful shutdown**: 배포/스케일인 시 `@Async` 즉시 발행이 유실되지 않도록 `spring.task.execution.shutdown.await-termination`과 컨테이너 `terminationGracePeriodSeconds`의 합을 맞춘다.
- **outbox 정리(purge)**: PUBLISHED 행이 무한정 쌓이므로 보관 기간을 정해 아카이브/삭제하는 배치를 둔다.
